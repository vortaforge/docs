Architecture

One core pack, 33 module packs, 22 hook slots and no module that knows another module exists. The last part is the design; everything else follows from it.

The shape

A datapack cannot call another datapack. There is no import, no dependency resolution and no namespace that can see across a pack boundary. So a modular engine cannot be built out of direct calls - the moment me_player_module calls me_perm_module, the two stop being independently installable.

macroEngine solves this the only way a datapack can: the core owns every seam, and modules only ever touch a seam. A seam is a #tag function tag. Modules add themselves to a tag; the core runs the tag. Neither side names the other.

core tick
  └─ function #me_core_module:hook/wand_tick   ← the seam (a tag, note the #)
       └─ me_wand_module:core/internal/wand/tick ← the module's entry

The module does not edit that tag. It ships a second file with the same tag id in its own pack, marked replace: false, and the game unions the two lists. Neither side names the other; both just declare the same tag.

An empty tag is a valid tick, and every contributed value is marked required: false. That is what makes a module removable: take the jar out and the tag has one fewer entry, no load error, no dangling reference. No module has to be told a sibling is gone, because no module was ever told a sibling existed.

The 22 hook slots

These are the entire public surface of the engine - 22 slots, each one a function tag owned by the core. A module that needs to run code at a particular moment adds itself to one of these and nothing else. The right column shows which modules currently attach to each slot; empty slots are not defects, they are extension points nobody has needed yet.

Two kinds of slot

Twenty of the 22 slots are fire-and-forget: the core runs the tag and does not read anything back. Those are cheap to extend, because a module can add itself without agreeing with anyone about anything.

Two slots return a value - perm_require and player_get_name - and those are the only places where two modules must agree on a contract. A query slot answers into a scoreboard holder that the caller then reads, so the holder name, the encoding and the "no answer" representation are all part of the seam.

KindCountCost to extendSlots
Side-effect20 Add yourself to the tag. Nothing else. all the rest
Query (returns a value)2 Add yourself and honour the scoreboard contract the caller reads. perm_require, player_get_name

Keeping that ratio at 20:2 is the reason the module set is extensible. Every new query slot is a new contract that every future module must be written against; a new side-effect slot costs nothing.

Where the files are

1,529 functions across 34 packs. The distribution is lopsided on purpose: the core carries the dispatcher, the queue, state, config and the kernel services, so it is expected to be the largest pack by a wide margin. A module that grows past the core is a sign the split is wrong.

Every module declares me_core_module as a hard requirement; the core declares nothing. There is no second-level dependency in the graph - me_perm_module does not require me_player_module even though it operates on players. It reaches the player API through a hook, which is the same mechanism it would use if the player module were not installed at all.

What the core owns

  • Dispatch - the entry point every command and tick passes through.
  • The deferred queue - work that must happen after the current function returns, since a function cannot re-enter itself.
  • State and config - the scoreboard-backed storage every module reads and writes.
  • Load and tick - the two function tags Minecraft itself calls, wired to the slots above.
  • Kernel services - math, rng, log, string, color, validate. Small, stateless, and duplicated nowhere.
  • Every extension point - the 22 slots. A module may not invent one.

What a module owns

Its own namespace, its own functions, its own config keys, and its own membership in the tags it needs. Nothing else. A module may not:

  • define a hook slot (tools/test_module_removal.py enforces it),
  • ship a core/internal/ tree,
  • call another module's functions - the namespace is not visible across packs anyway, so this fails at build rather than at runtime,
  • assume a sibling is installed. If me_player_module is absent, me_perm_module still loads and simply has no players to resolve.

Why this survives removal

The test is not "does it load without the module". It is "does the engine still tick when the module was never there". The difference matters: a missing tag entry is invisible, while a missing function call is a silent no-op that Minecraft reports as an error in the log and otherwise ignores.

All 34 packs pass the removal test individually. That is 34 builds, each with exactly one pack absent, checking that load and tick still complete.

The rule that keeps it honest: feature code never lands in core. Core grows only when a new seam is genuinely needed by more than one module - and a seam added for one module is a sign that module should own the work instead.
