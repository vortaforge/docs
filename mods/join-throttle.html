join-throttle

Rate-limits connection attempts per address. Five attempts in thirty seconds, per address, counted before the handshake completes.

What it actually does

It counts join attempts per client address inside a sliding window. When an address exceeds the limit, further attempts are refused during that window with denyMessage instead of reaching the server's own login handling.

It works at the connection layer, not in the game - the attempt is denied before a player entity exists. That is why it can stop a reconnect flood that the server would otherwise spend real work on.

Installation

  1. Drop the jar in mods/. Fabric Loader only; no Fabric API.
  2. Start the server once to create config/join-throttle.json.
  3. Adjust and restart.
Put it behind your proxy's real address. If the server sits behind Velocity or BungeeCord and does not forward the client address, every connection arrives from the proxy's address and one busy address throttles everyone. Enable address forwarding on the proxy first.

Settings

KeyDefaultWhat it does
maxJoins5 How many attempts an address may make inside the window before further ones are refused.
windowSeconds30 The length of the sliding window, in seconds. The count is not reset on a boundary; attempts older than the window stop counting.
denyMessage "Too many connection attempts. Please wait a moment and try again." The disconnect reason shown to a refused client. Keep it vague on purpose - a precise message tells an attacker exactly how much room is left.

Choosing values

The default

{
  "maxJoins": 5,
  "windowSeconds": 30
}

Five in thirty seconds. Generous for a person with a flaky connection - they can fail four times and still get in - and tight enough that a scripted flood is stopped almost immediately.

Strict, public server

{
  "maxJoins": 3,
  "windowSeconds": 60
}

Three in a minute. Catches slow-and-steady reconnectors. Raise it if you get complaints from players on mobile data, who legitimately drop and retry more than once a minute.

Whitelisted, private

{
  "maxJoins": 10,
  "windowSeconds": 15
}

Loose. The whitelist is the real boundary here; this setting only stops a runaway client, so it should never be the thing that locks out a legitimate player.

How attempts are counted

  • Per address, not per name. Two players behind one home router share a count.
  • Refused attempts count. Being throttled does not reset the window, so hammering extends the refusal rather than shortening it.
  • A successful join also counts. An address that joins five times in thirty seconds is at the limit even if all five succeeded.
  • State is in memory. A restart clears every counter. This is not a ban list and does not survive a restart.
  • IPv4 and IPv6 are separate addresses. A client that can reach the server over both is counted separately on each.

What it does not do

  • It does not ban. No permanent record, no allow-list, no staff command to lift a throttle - it clears on its own.
  • It does not distinguish a bot from a person. There is no CAPTCHA, no proof-of-work and no per-username logic.
  • It does not limit in-game actions. Once a player is connected, this mod has no further effect. Movement, chat and commands are not throttled.
  • It does not replace a firewall. A distributed flood from many addresses stays under the per-address limit by construction. This stops reconnection loops, not a botnet.
These are the shipped values. maxJoins = 5, windowSeconds = 30 and the default denyMessage come from ThrottleSettings, and every value is clamped by sanitized() before use - a negative window becomes the minimum rather than an unbounded window.
