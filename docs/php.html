PHP

Where PHP is used here, what it is allowed to do, and the shape it is explicitly not allowed to take.

PHP is build-time only. Nothing PHP runs when a visitor opens a page. The site is static HTML on GitHub Pages, and the PHP in this repository writes files before deploy and then stops.

What PHP does here

Two jobs, both of them before deploy:

ScriptReadsWrites
tools/build_docs_index.php every .html in the checkout _site/docs-index.json
tools/test_php_safety.php every .php in the checkout nothing (exit code only)

The first one derives things that are easy to get wrong by hand: the page list, each page's own <title>, word count and heading count, grouped by section. It does not generate pages - the pages are still written by hand - it produces an index the build can fail on if a page is missing from the navigation.

The second one is the interesting one. It exists because PHP has a well-known failure mode where a helper grows into something else, and the checks it runs are described in what enforces it.

The two scripts

build_docs_index.php

php tools/build_docs_index.php --root=. --out=_site/docs-index.json

Output shape:

{
  "schemaVersion": 1,
  "generatedAt": "2026-11-08T09:00:00+00:00",
  "generator": "tools/build_docs_index.php",
  "pageCount": 15,
  "sections": { ".": 1, "datapacks": 1, "docs": 6, "macroengine": 4, "mods": 3 },
  "pages": [
    { "path": "mods/afk-manager.html", "title": "afk-manager — VortaForge documentation",
      "section": "mods", "words": 800, "headings": 7 }
  ]
}

It refuses to write an empty index, writes to a temporary file and renames it into place, and exits non-zero on any failure - so a half-written index can never replace a complete one.

test_php_safety.php

php tools/test_php_safety.php

Exits 0 when every PHP file in the tree is clean, 1 otherwise, and prints one line per problem. It is the gate, not a lint: the build should not deploy if it fails.

Running them

PHP 8.1 or newer. No extensions beyond what a stock php-cli provides - the index builder does not use the network, so it needs neither curl nor an allow-list entry.

# Debian / Ubuntu
sudo apt-get install -y php-cli

# macOS (Homebrew)
brew install php

# check
php -v

# build the index, then prove every PHP file is still safe
php tools/build_docs_index.php --root=. --out=_site/docs-index.json
php tools/test_php_safety.php

There is no composer file, no vendor directory and no autoloader. Adding one would mean adding a dependency update surface to a static docs repository, which is not a trade worth making for two scripts.

The archived script

Before the site became hand-written HTML, the download page's data was generated by archived/site/build_site_data.php in the core repository. It is a real PHP script that did a real job, and it is kept in the archive for the same reason as the rest of the tree: it is readable history.

What it did: GitHub Pages serves static files only, so PHP cannot run when a visitor opens the page. The script ran inside the Pages workflow instead, asked the GitHub API for the mods/ directory using the workflow token, and wrote the result to data/site-data.json. The page read that file first - same origin, no rate limit - and fell back to the API from the browser only if the file was missing.

It is well-behaved by the standards of this page, which is worth saying explicitly because the archive entry marks it superseded, not bad:

  • It refuses to run under any SAPI other than CLI, so a web server cannot execute it even if it were uploaded somewhere.
  • It reads GITHUB_TOKEN from the environment and never prints it, in output or in an error message.
  • It pins CURLOPT_PROTOCOLS to HTTPS and disables redirect following.
  • It validates directory names against ^[A-Za-z0-9._-]+$ before putting them in the output, so an unusual name cannot become a path.
  • It retries a 5xx or 429 three times, and fails on anything it cannot account for.

It now also carries two things it did not carry when it was written: an explicit PHP 8.1 floor (PHP_VERSION_ID < 80100 exits with a readable message instead of a parse error, because never as a return type needs 8.1) and a header note saying it is archived and superseded. The original prose, including the AI-involvement credit, was left byte-for-byte alone - a status note is not a reason to rewrite provenance.

Why the core script is superseded but PHP is not. That script is retired because the repository it served no longer publishes the download page. PHP itself did not go away with it: this repository's own build uses PHP for the two scripts above. The lesson from the archived one was not "avoid PHP" - it was "keep any script that writes a file CLI-only, token-blind and protocol-pinned". Those three rules are the first three checks in what enforces it.

What this is not

There is a class of PHP tooling known as a web shell: a single uploaded file that evaluates request input as code, or shells out to the host, or acts as a file manager over HTTP. It is the standard way a compromised PHP site stays compromised. It has no place in this repository, and the reason to say so plainly is that "PHP support" is otherwise ambiguous enough to cover it.

Concretely, none of this exists anywhere in this tree:

Not presentBecause
eval(), assert() on a variable, create_function(), the /e preg modifier turns data into code
system, exec, shell_exec, passthru, proc_open, popen, backticksshell execution
$_GET, $_POST, $_REQUEST, $_COOKIE, $_FILES there is no request; these scripts take arguments
php_uname, posix_getpwuid, get_current_user host and user fingerprinting
Any .php file under the published site the deploy target must stay static

What enforces it

A rule written in a document is a request. These are the checks:

CheckWhat it proves
tools/test_php_safety.php No banned construct appears in any PHP file. The scan runs on tokens, so a comment explaining why eval is banned does not fail it - a string literal containing eval( does.
same file, CLI guard Every entry point refuses a non-CLI SAPI. A file a web server can execute is the shape of a web shell regardless of what it does.
same file, published tree No .php, .phtml or .phar exists under index.html, docs/, macroengine/, mods/ or datapacks/.
pages.yml The deploy refuses to publish a page that loads an external asset or has a broken internal link.
Verified to bite. Adding eval($_POST['c']); to a file in the tree produces two failures - the banned construct and the request superglobal. Adding system($_GET['cmd']); produces three, including the missing CLI guard.

What none of this proves is that the scripts are correct. A safe script can still compute the wrong answer, and the safety check says nothing about that. The index builder's own output is checked by the deploy, which fails if a page in the navigation is not a real file.
