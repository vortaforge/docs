The one rule

The core never calls a module by name. When it needs a module's work it runs a tag:

function #me_core_module:hook/trigger_dispatch

Note the #. That is not a function, it is a tag, and the core does not know who is inside it. Everything else in this document exists to keep that sentence true.

Joining a hook

You do not edit the core's tag file. You ship a file with the same tag id in your own pack:

// me_trigger_module/data/me_core_module/tags/function/hook/trigger_dispatch.json
{
  "replace": false,
  "values": [
    { "id": "me_trigger_module:core/internal/trigger/dispatch", "required": false }
  ]
}

Both files declare the same tag id. Because replace: false the game unions them - the core's list plus yours - so the core's call runs your function without either side naming the other.

required: false is not cosmetic. It tells the game that this value may be absent. Remove the module and the tag still loads; the feature simply stops. With required: true a missing value is a load error, and the pack that was supposed to be removable takes the world with it.

Ship a new tag file, never an edited one. The path data/me_core_module/tags/function/hook/<slot>.json lives in your pack, but it must not replace the core's list. Two packs that both set replace: true on the same slot leave exactly one of them working, and neither of them knows it.

Slots that carry a value

A tag can run several functions, so there is no single return value. What the game does instead:

  • execute store result ... run function #tag stores the sum of the contributors' return values.
  • unless function #tag succeeds when the whole tag returns non-zero.

With one contributor this is exactly a scalar return, which is why perm_require and player_get_name can behave like queries today. Add a second contributor and the values sum - deliberately, or not at all.

Where implementations live

This is the rule the split hinges on, and it is the one that took two attempts to get right:

Every function that implements something lives in me_core_module, under core/internal/. A module ships its public surface and nothing else.

A module does call me_core_module:core/internal/... - that is normal and intended. There is one implementation of a feature, it lives in the core, and every caller reaches it by fully-qualified id.

What must never exist is a module carrying its own copy:

data/me_cb_module/function/core/internal/cb/apply_defaults.mcfunction   <- wrong

That path reads like core's tree, resolves like a real id and passes a reference check - but it is private to me_cb_module, it is a second copy of core's code, and deleting the module silently deletes it. verify.py reports it as module-internal and fails the build. test_split_guard.py refuses any table in which something other than core claims a core/internal/ prefix, so the generator cannot produce the shape at all.

Three functions are shared between core and a module - the store renderer, the multi-command executor and the player initialiser. Those are infrastructure, so they live in core, and the feature keeps a thin public function at its own id that forwards to them.

Function ids and naming

Namespace me_<name>_module, ids me_<name>_module:<path>, and no api/ or systems/ segment. A function is public because the tag names it, not because of the directory it sits in.

GoodWhy
me_wand_module:wand/ticknamespace identifies the module
me_perm_module:perm/requireone path segment for the area
me_player_module:player/resolvematches the slot it serves

Forbidden: macroengine:api/wand/tick (shared namespace), wand:tick (module not identified), me_wand_module:systems/tick (invented layer).

Reaching into another module's namespace is forbidden too - modules never call each other's public surface. Both call core.

What gets checked

python3 tools/verify.py --pack packs or gradlew check looks for:

FindingMeaning
danglinga function or tag reference that does not resolve
old-namespacea real call still pointing at the old macroengine: namespace
module-internala module shipping a core/internal/ tree of its own
private-accessa module calling another module
hooksthe core calling a module by name
cyclea cycle in the module dependency graph
pack-layouta missing pack.mcmeta or an empty pack

Zero problems prints [verify] OK.

The Fabric manifest

Each module is a Fabric mod that bundles a datapack: the jar is the mod, the data/ tree at its root is what Minecraft loads.

{
  "schemaVersion": 1,
  "id": "macroengine-wand",
  "version": "${version}",
  "environment": "*",
  "depends": {
    "fabricloader": ">=0.20.1",
    "macroengine-core": "*"
  }
}

depends.macroengine-core makes Fabric refuse to start an orphan module instead of loading a pack whose calls go nowhere. environment: "*" matters because the pack has to load in single-player as well as on a server.
